# 随记现在是什么，接下来做什么

更新：2026-10-14。本文把原生功能与待讨论的设计分开。持续输入与回执等待版已更新两端，离线验证通过；S9 首次复测确认一处原有缺口明显改善，但全边界与无唤醒及时同步仍未通过。录音可靠性以 [真机验收](ACCEPTANCE.md) 为准，视觉基线沿用 [设计规范](DESIGN.md)。

## 一条主线

**戴着手表把一天可靠留下；需要时，在手机上找回原话、整理想法、办好明确交代的事情。**

Watch 负责采集和少量快捷操作；iPhone 负责保存、处理、检索和回顾。Bot 是有反馈的操作入口，不是额外的游戏或必须照顾的角色。全天记录是使用方式，不是已证明可以连续运行 24 小时的承诺。

用户已经选择保留可回听原声，默认 30 天，可调；转写文字继续保留。此轮不会再把“只留文字还是留原声”作为待决定问题，也不直接删除没有语音的环境声音。

## 当前真机能做什么

| 事情 | 当前原生状态 | 尚缺的部分 |
| --- | --- | --- |
| 手表持续记录 | 轻点开停、分段本地保存、离线缓存、恢复补传、手机确认后释放副本 | 后台补传仍可能积压；新采集路径一处缺口已改善，全边界与长时续航待验证 |
| 手机说一句 | 底部 Bot 控制手机本机录音，停止直接保存 | 不是遥控手表，也未把口述解析成可执行指令 |
| 转写 | 可配置通用 OpenAI 兼容语音接口，自动队列、失败重试；密钥存手机 Keychain | 真实后端准确率待测；两轮快转/精转、全天后台转写尚未完成 |
| 今天 | 真实录音时间线；相邻连续片段折叠；可进详情回听、保留原声、改文字、分享文字 | 按事件整理、睡眠/运动/地点、晨间规划及日/周/月回顾 |
| 记忆 | 关键词搜索已保存记录和转写 | 基于记录的 LLM 聊天、语音查询及来源引用 |
| 待处理 | 当前主要列未完成或失败的转写 | 尚不是提醒事项清单、AI 决策收件箱或 Agent 任务台 |
| 日记 | 独立日记录音有类型；长录中可标记日记起点 | 起点还不是完整日记区间；未自动整理或写入 Obsidian |
| 提醒与 Agent | 已有设计方向 | EventKit 双向同步、执行适配器与完成回执尚未实现 |
| 声纹、环境音、健康 | 研究与接口方向 | 尚未接入真实识别或 HealthKit 数据 |
| AirPods | 仍是后续的便捷输入与回听入口 | 麦克风路由、通话抢占和快捷启动尚未验收；不当作独立全天录音设备 |

浏览器原型演示过的聊天、提醒、晨间规划和周/月回顾，不等于这些能力已经接入当前 App。

## 现在的操作逻辑

| 场景 | 操作 | 实际结果 |
| --- | --- | --- |
| Watch 未录音 | 轻点 Bot | 开始持续录音；显示录音中和累计实际录音时间 |
| Watch 正在录音 | 轻点 Bot | 停止并保存，自动回待机；无需再点完成 |
| Watch 未录音 | 按住后右拖、松手 | 开始独立日记录音；左拖仍为持续录音 |
| Watch 正在持续录音 | 按住后左拖 / 右拖、松手 | 标记重点时刻 / 日记起点；不会停录或另开录音器 |
| 正在选手势方向 | 拖回中央松手 | 取消选择，不产生新操作 |
| 独立日记首段尚未提交 | 向下拖动松手，或点取消 | 丢弃这次草稿；持续录音已保存的片段不这样删除 |
| 系统双指互点 | 对当前可见 Bot 主按钮执行 | 与轻点开停相同；尚需独立佩戴验收，不是后台全局手势 |
| iPhone 底部 Bot | 点一次 / 再点一次 | 手机本机开始录音 / 停止保存；不改变手表录音 |
| iPhone 记录详情 | 回听、更正、保留、分享 | 针对这条实际记录；没有成功保存的外部执行结果不显示为完成 |

标记目前只是时间书签，不等于 AI 已识别重点，更不等于提醒已创建。没有标记也应能回顾和搜索。

## 5 分钟、15 分钟分别是什么

当前原生实现从首版起每 5 分钟保存一个文件。这是工程初版取值，目的是让长录能分批保存、恢复和处理，尚未证明是最优参数。用户看到的应是连贯的记录，不需要管理每个文件。

AUDAY FAQ 说的是通常每 15 分钟**准备自动同步**，没有在该说明中披露文件分段长度。[AUDAY FAQ](https://auday.ai/faq)

三件事应分别设计：麦克风是否持续采集、音频文件多长封存一次、何时传给手机。不能通过把 5 分钟改为 15 分钟来声称解决交接漏音，也不应每保存一段就要求用户打开手机。固定声源短测曾确认一处约 1.6 秒漏音；已改为保持采集、只切文件，首次 S9 复测该处误差约 0.2 ms，但其他边界证据不足，仍需完整验收。

## 本轮建议，尚未改动交互

1. **先让后台工作自动完成。** 正常排队、重试和处理不进用户待办；只在需要人处理的权限、容量或持续失败时提示。已有文件始终可用，状态分别说明已保存、待同步、待转写，避免把一项成功当成全部成功。不要求用户关闭低电量模式、打开手机或唤醒手表作为日常同步步骤；系统延后交付时，自动保留与补传，送达时限另行验证。
2. **减少日记与主动口述的模式记忆。** 下一版可探索按住 Bot 说一句，松手结束主动区间，拖开取消；由“记个日记”“提醒我明天……”这些明确口述表达意图。持续录音中只标注这段主动区间，不为了口述停掉全天录音。此方案需先验证手势冲突与区间结束行为，当前没有上线。
3. **保留可见导航，不把 Bot 变成万能摇杆。** 今天/记忆/待处理仍有普通入口，Bot 专注录音和提问。主题是外观偏好，不用颜色承担用户必须记住的页面含义。
4. **今天看现在，记忆帮找回，待处理只收需要决策的事。** 转写排队不应长期挤占待处理。记忆聊天的每个事实能跳回日期、原文和仍在留存期的原声；未知就说明，不生成不存在的记录。
5. **先做有来源的回顾，再做更多自动执行。** 明确主动说出的提醒可走提醒事项；从被动谈话推断的事项先作为候选。Agent 交接与完成各有回执；不能把“发出了请求”写成“事情办完了”。

## 手机最后应当帮人做什么

- **今天：看当下。** 打开定位到现在，录音、主动口述、提醒、运动和睡眠按真实时间连在一起。睡眠是自己的时间段，显示时长、阶段与实际可取得的指标，不给整天每条记录挂睡眠标签；没有数据就不编造分数。
- **记忆：找过去。** 既能搜索“昨天那个视频选题”，也能对话询问，答案给具体来源。周/月视图帮人看重要想法、事项推进及睡眠/运动变化，并能点回当天；相关变化不直接写成健康因果结论。
- **待处理：少操心。** 只放需要确认、纠正或授权执行的候选，例如模糊的提醒时间或尚未决定交给哪个 Agent 的任务。已明确创建的提醒回归系统提醒事项，双向同步完成状态；日記归档到 Obsidian 后仍能从来源找回。

按 Apple 的交互取向，主动作需要可见、可预测，状态和取消路径清楚；按 Claude 式克制风格，Bot 可以有轻微呼吸、倾听与回应，但不遮挡时间线、不要求记住各色动作。这是设计取向，不是对两家未发布产品的断言。AI 的价值体现在理解明确口述、找回依据、把任务办完；不依赖用户先学会拖动角色切页。

## 从参考产品真正借什么

- AUDAY：少操作的全天捕获、手机整理、从回顾跳回原文和原声。标记保持可选，不照搬另一套轻点/长按含义。
- Omi：可检索记忆与开放接口；离线能力必须按硬件版本验证，不把官网文案当可靠性证据。
- Bee：每天开启后少打扰、日终帮人减负。随记已经选择留原声，因此不照搬实时删除原声的策略。
- Plaud：明确开录、结束即保存、离线先留住。主动会议记录设备的使用前提与全天被动采集不同。
- Limitless：记录需要能独立导出，换服务或服务结束后仍可访问。

对应的一手来源、版本及限制见 [产品参考研究](PRODUCT_REFERENCE_REVIEW_2026-10-13.md)。接下来先把无感同步与连续采集做扎实，然后接真实转写、来源问答、提醒事项和 Obsidian；健康和周/月回顾沿用已确认方向，不在可靠性欠缺时靠新增功能填补。
